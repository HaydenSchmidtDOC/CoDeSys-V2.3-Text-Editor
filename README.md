# CoDeSys V2.3 Text Editor for VS Code

A VS Code extension + reverse-engineering toolkit for reading and editing CoDeSys V2.3 / Beckhoff TwinCat `.pro` binary project files directly, without needing a manual TwinCat export.

## What it does

When you open a folder that contains a `.pro` file, the extension mounts it as a **virtual folder of Structured Text (`.st`) files — one per POU**. A "CoDeSys POUs" view in the Activity Bar lists every `.pro` in the workspace; expanding one shows its POUs as `.st` files. Clicking a POU opens it as a normal text file with ST syntax highlighting; saving writes the edit back into the `.pro` binary (with a syntax gate + round-trip safety net).

## Background

TwinCat PLC Control (CoDeSys V2.3) project files (`.pro`) are a proprietary binary format. Opening one in a plain text editor shows NULs — the source isn't stored as a simple text blob. This project reverse-engineers enough of that format to decode and edit Structured Text (ST) POUs directly from the binary, and best-effort decodes Ladder Diagram (LD) networks (still read-only).

## Contents

- **`pro-viewer-extension/`** — A VS Code extension (`codesys-v2-text-editor`) that mounts `.pro` files as virtual folders of `.st` files:
  - `virtualfs.js` — a `FileSystemProvider` mapping `codesys-pou://` URIs to `.st` content (read = `decodePro`, write = `applyPouEdit`).
  - `treeview.js` — auto-discovers `.pro` files in the workspace and lists their POUs.
  - `uri.js` — URI helpers built on `vscode-uri` (robust path encoding).
  - `decoder.js` — the binary decode/encode engine (the core reverse-engineering value).
  - `stcheck.js` — a lightweight ST syntax checker used as a save-time gate.
  - `syntaxes/st.tmLanguage.json` — a minimal ST TextMate grammar for highlighting.
  - Install via `code --install-extension pro-viewer-extension/codesys-v2-text-editor-0.2.0.vsix`. Self-checks: `node pro-viewer-extension/test_decoder.js`, `test_stcheck.js`, `test_virtualfs.js`.
- **`_extracted_pous/`** — A one-off snapshot of decoded POU source extracted early in this project (via the extension's export command). It's just prior output, not a ground truth — the real ground truth used to validate everything below is a manual TwinCat "Export" (`.EXP` text file) of the real project, kept locally alongside the `.pro` and gitignored (not part of this repo).
- **`_scratch/`** — Python/Node scripts used to reverse-engineer the binary format: printable-run scanning, POU boundary detection, and byte-level correlation against `.EXP` exports (including a controlled before/after edit — see below).

## Status

### Structured Text (ST) POUs — decode + edit + save

- **Decode: validated.** Each POU's declarations + implementation are printable ASCII/CRLF text in the binary, framed by non-printable bytes. Confirmed byte-for-byte against a real CoDeSys export.
- **A POU's ST source is stored as TWO printable runs, not one.** The header + declaration block is one run; then a short non-printable gap containing the `0x12` separator byte and a 16-bit little-endian length; then the implementation body (exactly `len` bytes) as a second run. The decoder joins them (reinserting a CRLF at the seam). This is what recovers the full ST body — e.g. `UPS_CX80xx`'s FB call — without sweeping in the Visualization data that follows the implementation. Verified across all 13 ST POUs in the corpus (single-byte lengths like UPS's 187 and multi-byte like MAIN's 3072 both decode correctly).
- **POU boundary is run-based, not inferred.** Each POU's text ends at the end of its own printable run (the next non-printable framing byte), capped at the next POU's start as a safety net. This fixes the old leak where the *next* POU's header (and any forward-link) could be swept into the current POU's text (the UPS/TwinSafe symptom). The old comma-based "trim the leaked tail" heuristic is gone.
- **One known artifact, handled correctly (not just papered over):**
  - A single non-printable framing byte is sometimes dropped between a POU's `END_VAR` and whatever follows on the same line (commonly `END_VAR(*comment*)`) — the missing CRLF is reinserted to recover the real formatting.
- **Write support: variable-length.** An edit no longer has to keep the POU's byte length identical. Saving finds the common prefix/suffix between the old and new text (anchored to real source byte positions, tracked per-character through both artifact-repairs above) and replaces only the differing middle span, shifting everything after it in the file. This was validated against a real controlled test: renaming a variable (`InterfaceBagReleaseAct` → `...withaddedbytes`, +14 bytes) round-trips exactly and leaves every other POU byte-for-byte unaffected.
  - **Two-run length prefix is patched on write.** For two-run ST POUs, the implementation body's length is stored in a 16-bit little-endian prefix after the `0x12` separator. When an edit changes the body's length, `applyPouEdit` now locates that prefix (scanning backward from the splice) and patches it, so the body re-decodes at its full new length instead of being truncated to the stale length.
  - **Why this is believed safe:** a systematic search of the real `.pro` file found no absolute byte-offset table anywhere referencing POU text locations (POU "directory" entries only carry a name + timestamps), and no whole-file checksum. That's evidence, not proof — every save is still verified by re-decoding the whole file afterwards and refusing to write if the edited POU doesn't decode back to exactly what was typed, or if *any other* POU's decoded text changed as a side effect.
  - A recursive-descent syntax check (`stcheck.js`) runs before every save — it strips comments/strings (so keywords inside them don't count), tracks block nesting with a stack, and catches unbalanced or out-of-order blocks, a stray `ELSE`/`ELSIF` outside an `IF`, a declaration keyword inside the implementation (and vice versa), and unbalanced parens/brackets. **Errors block the save; warnings do not.** Undeclared identifiers are warnings, not errors, because in a multi-POU project a POU legitimately references globals declared elsewhere. It is still not a full IEC 61131-3 parser (no type compatibility checking) and is not a substitute for a Rebuild in TwinCat.
  - Of the real project's 27 POUs, 21 currently qualify as editable; the other 6 are the Ladder Diagram POUs below.

### Ladder Diagram (LD) POUs — decode only, always read-only

LD POUs (`CanopyControl`, `ControlledBuffer`, `GlobalFlags`, `HybridControl`, `Intrusion`, `RearTrack`) use a different encoding: every contact/coil/FB-instance/time-literal reference is stored inline as a `[tag byte][length byte][ASCII name]` micro-record, repeated at (almost) every use site.

**Confirmed, used by the decoder:**
- Tag byte reliably identifies the record class: CONTACT (`0x0B` base), OUTPUT (`0x00`=POSITIV/NO_SET, `0x02`=POSITIV/SET, `0x03`=NEGATIV/SET), FB-instance name (`0x05`/`0x45`), time literal (`0x41`). Zero contradictions across all 6 POUs.
- `0x80` on a CONTACT tag = negated. Zero contradictions across 155 aligned contacts.
- Network boundaries are marked by an `08 FF` byte pair somewhere in a small lookback window before a network's first record (the gap varies 0–3 filler bytes — it's not always adjacent, which broke the network split for `HybridControl` until fixed and validated against a real TwinCat screenshot).
- **AND/OR grouping is a real nested tree — cracked via a long series of controlled A/B edits.** A single "network combinator" byte was the first, too-simple theory (validated only for a 2-contact network flipped `OR → AND` in TwinCat). A second edit (a 6-contact network regrouped) falsified it: the header byte stayed constant while real internal structure changed. The actual grammar, found by re-framing the problem as rail *splits and joins* rather than "one combinator per network": between two contact records, any stray byte the old scanner silently skipped over **opens a new bracketed group** — `0x09` = AND-group, `0x0A` = OR-group. A contact's own tag byte can carry `0x40`, which **closes the innermost open group**, that contact being its last member. A group left open when the network's last contact is reached needs no explicit close (it auto-closes). This is a simple stack machine, and it was validated against a large batch of real edits: swapping which variable sits in which branch, moving whole groups' positions, and building networks with 2-way/3-way/4-way and nested splits — every one reconstructs into exactly the expression the edit was known to produce.
  - `0x40` also sometimes appears standalone on a group-*open* byte (`0x0A→0x4A`, `0x09→0x49`). Several theories for what this extra bit means were tried and falsified (first vs. later sibling group, group content/identity) - current best guess is it marks the "rightmost spine" of the tree (an open whose eventual close chains straight through to the network's end with no further opens in between), which looks like a redundant/derivable serialization artifact rather than fresh logical content. The decoder does **not** rely on it — only the low nibble of an open byte (AND vs. OR) is used to build the tree.
  - Re-run against every network in every LD POU across the full test corpus (7 real `.pro` files, ~140 networks): zero networks fall back to the flat "MIXED, unresolved" rendering now. One caveat flagged by a second, independent read of the same data (not yet resolved): in one network, a variable that should likely be a coil/output decodes with a plain contact tag — suggesting coils may not always be distinguishable by tag byte alone. Treat any single decoded network with healthy skepticism until cross-checked.
- **Timer/FB-instance calls (TON/TOF/R_TRIG/...) decode too, not just their names.** An FB-instance record (tag `0x05` non-terminal / `0x45` terminal) participates in the exact same AND/OR open/close grammar as a contact — confirmed against `ControlledBuffer`/`HybridControl`'s real `RunToRearTimer`/`RunRelJamTimer`/`RunToReleaseTimer` timers, byte-for-byte against a TwinCAT export. Its PT operand (if any) is the next record (tag `0x41`); the FB's type name follows as a bare, tag-less length-prefixed string when a PT is present (e.g. `03 54 4f 4e` = `"TON"`), or as an ordinary tagged (`0x40`) record when there's no operand (e.g. `R_TRIG`). A fixed trailer follows the type name and must be skipped precisely, since the very next gap byte can legitimately open a *nested* AND/OR group (confirmed against `HybridControl` NETWORK 16's cascade, `RunRelJamTimer OR (InductPE1 AND RunToReleaseTimer)` — treating the trailer as a garbage "open" byte silently flattened this into a wrong 3-way OR before the fix). The trailer is 8 bytes (`01 00 00 00 00 00 00 00`) for timer types (TON/TOF/TP, which have a PT operand) and 6 bytes (all zero) for edge-detect types with no operand (`R_TRIG`/`F_TRIG`) — confirmed identical across every instance of both shapes in the corpus (`BagFound`, `PEHit1`, `PEHit2`). Cross-checked against every FB call site (24) in every one of the 7 corpus `.pro`/`.exp` pairs: exact match on instance name, type, and PT.
  - **Rendering matches the real project's own ST convention, not a raw dump.** Rather than inlining `Name:TYPE(PT:=...)` into the boolean condition, each FB instance is emitted as its own one-line call statement before the `IF` — `RunToRearTimer(IN:=BRRunToPE, PT:=T#6000ms);` — mirroring how the same FB types are called in the project's real ST POUs (e.g. SecurityDoor's `OpenTriggerFilter(IN:=OpenDoor, PT:=t#100ms);`). Edge-detect types (`R_TRIG`/`F_TRIG`) use `CLK:=` instead of `IN:=`/`PT:=`, again matching the project's own convention (`UpperPEEdge(CLK:=OpenPEFilter.Q);`). The condition then references the FB's `.Q` output where it sat in the tree. Each FB's `IN`/`CLK` is wired from the element(s) *immediately preceding* it in the same AND-chain (the rail's power at that point) — NOT the whole accumulated condition — so the call line and the `IF` don't duplicate each other. Validated against `HybridControl` NETWORK 16: the first (non-terminal) timer gets `IN:=BRRunRel`, the second (nested one branch deeper) gets `IN:=InductPE1` (its immediate predecessor), and the `IF` reads `BRRunRel AND (RunRelJamTimer.Q OR RunToReleaseTimer.Q)`.
  - **Known unresolved case: `Intrusion` NETWORK 2.** A 3-level-deep structure (`AND:2[ OR:2[ AND:3[...], AND:3[...] ], SuppressForBag ]`, confirmed from the real TwinCAT export) decodes with `SuppressForBag` incorrectly left as a 3rd member of the `OR` instead of a sibling of it. Root cause: `SuppressForBag`'s closing tag bit (`0x40`) has zero preceding gap bytes, and our stack model always pushes a leaf into the *currently open* group before applying its own close bit (pop-after-push) — correct for every other confirmed case (e.g. `RunToReleaseTimer` in the same file, which genuinely IS the last member of the group it closes), but wrong here, where the leaf needs to pop out to its *grandparent* group before being added. Nothing in the byte stream at that position distinguishes "I'm the last member of the group I'm closing" from "I actually belong one level further up" — needs more controlled test-file edits in TwinCAT to find the real signal (if one exists) before this can be fixed with confidence rather than guessed at. Does not affect `treeOk` (no crash/fallback), just silently produces the wrong nesting for this one case so far.
- LD POUs remain **always read-only** regardless of how cleanly they decode — write-back for ladder logic hasn't been implemented.

**Do not treat decoded ladder logic as authoritative.** This drives real physical equipment (airport baggage handling conveyors/doors). Cross-check any rendered ladder logic against a real TwinCat export before acting on it or changing a live system.

## Known gaps

- **LD write-back.** Decode-only; even confidently-decoded nested AND/OR trees can't be edited and saved yet.
- **Coil vs. contact tag ambiguity.** At least one real network has what should likely be a coil/output decoding as a plain contact tag — needs investigation before trusting output identification everywhere.
- **No POU add/delete/rename.** The editor can only edit existing POUs in place.
- **LD detection is marker-based, not ratio-based.** A POU is treated as ladder (read-only) if its post-`END_VAR` region contains the confirmed `08 FF` network-boundary byte pair — a positive structural signature that plain text never contains. This deliberately avoids the old "majority-binary = ladder" heuristic, which wrongly locked "poor" Structured Text (ST with dropped framing bytes / interleaved junk, e.g. UPS) as read-only. An unlisted ladder POU with no `08 FF` marker would be left editable and should be added to `KNOWN_LD_POUS`.
- **No live TwinCat 2 open/save test yet.** Everything above is validated by re-decoding our own output, not by confirming TwinCat 2 actually opens a file we've written. Do this before trusting a saved file on a live system.
